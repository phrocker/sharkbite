# Gateway recovery commitment

Issue [#169](https://github.com/phrocker/sharkbite/issues/169) tracks safe recovery of an external action after a gateway loses a response or its claim lease. The persisted record foundation came first. The runtime protocol lets a trusted gateway send under its first live claim after durable Prepare acknowledgment. A later live claimant may send the identical request only for a committed `key` or `natural` recovery mode. Legacy, missing-commitment and `unprotected` replays are refused.

## Claim and recovery protocol

1. The gateway pulls a queued first action or a lapsed prepared action. It calls the versioned `/claim-prepared` route. The server atomically records protocol version 1 on the first claim. A later claim requires that marker and the original key/natural commitment. The public claim answer always withholds both `Input` and `ExecutorKey`. The legacy remote `/claim` route refuses before calling the Claim service. An old gateway cannot receive executable material from the upgraded HTTP server; a new gateway receives a refusal from an old server lacking `/claim-prepared`.
2. The current authenticated claimant calls `/material` with the claim ID and exact fence while the lease and deadline remain live. The response contains only that action's Input and ExecutorKey, and no commitment digests. Material is not a send grant.
3. The gateway binds a request locally and computes a versioned digest of its method, complete URL, canonical noncredential headers (including the idempotency key), and binary body. It separately digests the required stable, nonsecret `-target-scope` account/tenant identifier. The target credential is attached only when sending and is never in the digest. An operator must keep target scope constant across replicas and credential rotations and change it when the target's deduplication scope changes.
4. The current authenticated claimant calls `/prepare`. The server rechecks identity, the current claim ID and fence, lease, deadline, live descriptor chain, protocol marker and declared external effect, then atomically records the write-once commitment on the first claim. On a later claim it compares the candidate mode, request, and target scope against the original commitment without rewriting it. An exact retry after a lost Prepare answer returns the same commitment only while that claimant still holds the live lease. After the first durable Prepare write, the server re-reads the current claimant and refuses to acknowledge a Prepare whose lease, deadline, or authorization expired during storage IO; the worker receives no send grant. The authenticated receipt echoes mode and both digests so the gateway can reject a substituted receipt for a different bound request. These digests stay off ordinary Pull, Status, MCP and logs. The gateway requires a matching receipt before SEND; its send gate checks a conservative local lease deadline before each target attempt. That deadline is anchored to the local monotonic instant when Claim was sent and to the server's lease duration, so worker/server wall-clock offsets do not extend it.

A lost Claim answer may be retried with the original expected version only before Prepare advances the record. A lost Prepare answer may be retried with the identical digests under the same live claim. An indeterminate or malformed answer grants no send. Material/Prepare refusal is logged and reported as `request_not_sent`; the action remains claimed until the lease expires. A later key/natural claimant can recover only when the original commitment exists and the bound request and target scope still match. Drift, legacy records, and unprotected routes require operator reconciliation. Authorized HTTP Status/Pull responses and MCP action results expose only commitment version, mode, original prepared fence and time; they never publish the digest of a potentially guessable request or the target account scope. Recovery-route refusals carry a closed `Shoal-Recovery-Refusal` code (`legacy_claim`, `missing_commitment`, `unprotected_replay`, `mode_drift`, `request_drift`, or `scope_drift`), which the gateway logs without request bytes or credential scope. Locally skipped legacy/unprotected offers are logged once per version. A replacement claim that cannot Bind, cannot send new bytes, or sees a target rejection remains nonterminal: its current-fence `request_not_sent` or `outcome_unknown` report does not resolve the earlier possible effect. The gateway logs `bind_failed`, `no_new_send`, or `replacement_unresolved` for operator reconciliation. Only a target success under the committed key/natural request can complete a replacement claim.

## Deployment boundary and limits

Every Fleet storage mutator and gateway worker must be upgraded or drained before the prepared protocol is activated. An old gob reader can ignore the new record fields and later re-encode a mutation that drops the commitment. A still-running old server can continue serving the legacy claim path. The first-send gateway also depends on the Claim response-binding checks in [PR #167](https://github.com/phrocker/sharkbite/pull/167); those must be deployed before activation. These are rollout requirements, not mixed-version persistence guarantees.

This protocol binds a trusted gateway's request to its durable Fleet record. The server cannot observe the target bytes, verify delivery, or stop a malicious custom worker that ignores the gateway protocol. Cross-claim recovery compares the persisted mode, request and target scope and relies on the target's documented deduplication guarantee. It does not prove the target honored that guarantee. Unprotected requests and legacy records remain refused.
