# Gateway recovery commitment (foundation)

Issue [#169](https://github.com/phrocker/sharkbite/issues/169) asks the effects gateway to distinguish a safe replay of an external request from a changed route, credential scope, or payload. The durable `fleet.ActionRecord.RecoveryCommitment` is the record foundation for that protocol. **This change does not enable replay, change gateway sends, or expose a Prepare API.** In particular, the presence of a record field is never itself permission to send.

## Durable record contract

The commitment is optional for old records and write-once on the first claim. It has protocol version 1, the selected recovery mode (`key`, `natural`, or `unprotected`), a digest of the complete bound request, a separate digest of a stable target account/credential *scope identifier*, and its original claim fence and UTC prepare time. The store rejects removal or modification after the first write. A lapsed legacy claim cannot acquire a commitment after another worker might already have sent. The model validates shape; it does not decide whether a claimant is currently authorized.

The request digest needs a versioned canonical byte encoding, including the method, full target URL, non-credential headers (including any idempotency key), and body. The scope identifier must be configured by the operator for each target account or credential boundary; it must not be inferred from a rotating credential or from the hostname alone. Each component needs an explicit length and stable ordering, and the future implementation must test header canonicalization and binary bodies. The exact encoding will be defined and implemented with the Prepare API, before any caller can write a commitment. No code in this foundation computes a request digest.

The digests can reveal low-entropy requests through guessing. They must stay internal to the authenticated comparison path. Ordinary Pull, Status, MCP, logs, and operator projections should expose at most the mode, commitment version, and a bounded refusal reason, never either raw digest or a credential. The current public projections do not include the new field.

## Required protocol before activation

1. Upgrade or drain every server that can mutate Fleet records **before** enabling prepared actions. An old gob reader can ignore this new field and re-encode a later mutation without it, erasing the commitment. Additive gob decoding is not a safe mixed-version persistence guarantee. The external-effect Claim response then withholds **both** `Input` and `ExecutorKey`. Withholding only the key would leave unprotected routes able to send. Old gateways therefore fail before SEND; this is an intentional mixed-version rollout boundary that needs explicit deployment sequencing. An upgraded gateway must fail closed against an old server with no prepare support.
2. An upgraded claimant uses a versioned authenticated material step to obtain `Input` and `ExecutorKey` while it still holds the live claim, then binds the exact target request. Material is *not* a send grant. The authenticated Prepare operation rechecks the current claimant identity, claim ID, exact fence, and live lease. It compares the versioned request and scope digests, then writes the commitment before acknowledging the first send. An exact retry after a lost answer returns the same committed result **only while that claimant still holds a live lease**. The version increment must leave fence-based Extend and Complete usable.
3. A later claim may send a keyed or natural request only if the mode, target scope, and bound request all match the durable commitment. It must refuse unprotected replay and any changed request, route mode, scope, or absent legacy commitment. An unknown Prepare outcome, lost lease, and restart before durable acknowledgment all block sending. A same-claim retry remains subject to the same live-lease check.
4. The trusted gateway must send the request it prepared and use the target's documented deduplication semantics. The server cannot independently observe target bytes, prove delivery, or make a non-idempotent target safe. A record without a matching acknowledged prepare is never a replay grant.

Tests for the complete protocol must cover first claim, crash/restart and identical keyed recovery, mode/request/scope drift with zero target hits, unprotected and legacy replay refusal, lost Prepare response, expired or replaced claim, old-client/new-server and new-client/old-server behavior, and the absence of digests and credential material in public projections. This foundation tests only record persistence, restart, immutable commitment, and rejection of retroactive commitment on a later claim.
